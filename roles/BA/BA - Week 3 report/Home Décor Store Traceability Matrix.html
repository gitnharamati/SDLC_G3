Every requirement from the Requirements List traced back to its acceptance criterion in User Story 1 or 2 (or to a resolved question), and forward to the test cases that verify it. Reading the matrix

  • US1-ACn / US2-ACn number the acceptance criteria in the order they appear in each story. US1-AC10 to AC13 are the named criteria (All options required, Search by room, Full catalogue page, Multi-item adds). US2-AC8n is the "word of caution" note on system-controlled statuses; US2-AC10 to AC12 are Catalog hierarchy, Product placement and Graphics per level.
  • RQ1–RQ5 are the resolved questions: payment simulator, order contesting, stock per size/color, options per product, email/SMS notification. RQ4 is narrowed by D6: Release 1 options are Size and Colour.
  • D1–D6 are the decisions recorded in the Increment 2 spec (delivery line, cart lifetime, search scope, out-of-stock listing, order of work, Size and Colour). D5 sets the order of work and maps to no single requirement.
  • Spec rules come from the three specs: SI, CH, OP (Increment 1); BR, FL, NR, PP, CT, AE (Increment 2); CO, PL, ST, PS, CP, OL, NT (Increment 3 analysis, draft). The Should-have requirements for Increment 4 have no rules yet.
  • Status records what week 2 QA found: Passed, Passed with a note (an observation), Open defect (BUG-01 to BUG-03), or Not run yet. Detailed results stay in QA's sheet.
  • Test IDs follow TC-<requirement>-<nn>, so a failing test points straight back to its requirement.
  • NFR-01 also gets a phone/desktop smoke pass at the end of each increment (weeks 3, 5, 7); the full run is in week 8.
  • Test cases verify each requirement against the criterion's Given/When/Then. Expected results, test data and execution status belong in the test management tool, keyed by these IDs.
